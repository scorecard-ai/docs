Scorecard's [Model Context Protocol](https://modelcontextprotocol.io) server lets an AI assistant work with your Scorecard data: create projects, testsets, and metrics, look up runs and records, and summarize results. Ask in plain language, and the assistant writes and runs the API calls for you.

## Connect

The hosted server is at `https://mcp.scorecard.io/mcp` and uses the Streamable HTTP transport. Sign-in happens in your browser through OAuth, so you don't need an API key.

<Tabs>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http scorecard https://mcp.scorecard.io/mcp
    ```

    Run `/mcp` in Claude Code to sign in. The [Scorecard plugin](/intro/ai-assisted-setup) also adds the server.
  </Tab>
  <Tab title="Claude Desktop and claude.ai">
    Open **Settings → Connectors**, click **Add custom connector**, paste `https://mcp.scorecard.io/mcp`, then click **Add** and **Connect** to sign in.
  </Tab>
  <Tab title="Cursor">
    Add the server to `.cursor/mcp.json`:

    ```json .cursor/mcp.json
    {
      "mcpServers": {
        "scorecard": { "url": "https://mcp.scorecard.io/mcp" }
      }
    }
    ```
  </Tab>
  <Tab title="Codex">
    ```bash
    codex mcp add scorecard --url https://mcp.scorecard.io/mcp
    ```
  </Tab>
  <Tab title="Gemini CLI">
    ```bash
    gemini mcp add --transport http scorecard https://mcp.scorecard.io/mcp
    ```
  </Tab>
</Tabs>

Any other client that supports remote MCP servers over Streamable HTTP can use the same URL. For CI or a client that can't complete OAuth, send an API key instead:

```json
{
  "mcpServers": {
    "scorecard": {
      "url": "https://mcp.scorecard.io/mcp",
      "headers": { "Authorization": "Bearer ak_..." }
    }
  }
}
```

An API key acts with organization-level permissions. Signing in with OAuth acts as you, with your role.

## Try it

Once connected, ask for what you need. For example:

<Prompt description="Create a project and a testset.">
Create a project called "Support Bot Eval". Add a testset called "Support Scenarios" with inputs `customerMessage` and `category`, expected output `idealResponse`, and 10 testcases covering billing, technical, and product questions.
</Prompt>

<Prompt description="Create metrics.">
Create two AI metrics in that project: "Response Accuracy" (integer 1-5), how well the response answers the question compared to the ideal response, and "Tone" (boolean), whether the response is professional and empathetic.
</Prompt>

<Prompt description="Analyze a run.">
For the latest run in "Support Bot Eval", which testcases scored lowest on Response Accuracy, and what do they have in common?
</Prompt>

<Prompt description="Compare projects.">
For every project in my organization, find the most recent run and report the pass rate on each Boolean metric.
</Prompt>

Name your fields and say which are inputs and which are expected outputs; the assistant guesses otherwise. The assistant sometimes gets a call wrong, looks up the SDK docs, and retries. That's expected.

## How it works

The server uses **Code Mode**. Instead of one tool per endpoint, it exposes two tools, and your assistant writes code against the [Scorecard TypeScript SDK](https://github.com/scorecard-ai/scorecard-node):

| Tool | What it does |
| --- | --- |
| `search_docs` | Searches the SDK documentation for the right method and parameters. |
| `execute` | Runs the TypeScript your assistant writes against a signed-in SDK client in a sandbox, and returns only what the code returns or logs. |

Filtering and aggregation happen inside the sandbox, so only the final result comes back to the conversation. A question that spans many projects or large records completes in one call. Each call is independent, and the sandbox can reach only the Scorecard API.

Metric group methods aren't available inside `execute`.

## Run the server locally

You can also run the same server on your machine with an API key:

```json
{
  "mcpServers": {
    "scorecard": {
      "command": "npx",
      "args": ["-y", "scorecard-ai-mcp@latest"],
      "env": { "SCORECARD_API_KEY": "ak_..." }
    }
  }
}
```

In Claude Code: `claude mcp add scorecard --env SCORECARD_API_KEY="$SCORECARD_API_KEY" -- npx -y scorecard-ai-mcp@latest`.

<Warning>
  The local server runs `execute` code in a [Deno](https://deno.land) sandbox, so Deno must be installed and on your `PATH`. Use Deno 2.8 or earlier.
</Warning>

To limit what the assistant can do, add flags to `args`:

- `--code-allow-http-gets` allows only read requests.
- `--code-allowed-methods` and `--code-blocked-methods` take regular expressions matched against SDK method names such as `records.delete`.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Only two tools show up">
    That's expected. The assistant reaches every API operation by writing code for `execute`.
  </Accordion>
  <Accordion title="The assistant gets an authentication error">
    OAuth sessions can expire. Disconnect and reconnect the server in your client's settings to sign in again.
  </Accordion>
  <Accordion title="The server doesn't appear in my client">
    Check the URL, `https://mcp.scorecard.io/mcp`, finish the sign-in flow, and restart the client.
  </Accordion>
  <Accordion title="The local server says Deno is required">
    Install Deno 2.8 or earlier and make sure it's on your `PATH`, then restart your client.
  </Accordion>
</AccordionGroup>

## Migrating from the per-endpoint tools

Earlier versions of the server exposed one tool per API operation, such as `list_projects` or `create_testsets`. Those tools no longer exist. Prompts written in natural language keep working, because the assistant now reaches the same operations through `execute`. If you referenced tool names directly, the table below shows where each one went.

<Accordion title="Old tool → SDK call mapping">

| Old tool | SDK call inside `execute` |
| -------- | ------------------------- |
| `list_projects`, `create_projects` | `client.projects.list()`, `client.projects.create({...})` |
| `list_testsets`, `get_testsets`, `create_testsets`, `update_testsets`, `delete_testsets` | `client.testsets.list(projectId)`, `.get(id)`, `.create(projectId, {...})`, `.update(id, {...})`, `.delete(id)` |
| `list_testcases`, `get_testcases`, `create_testcases`, `update_testcases`, `delete_testcases` | `client.testcases.list(testsetId)`, `.get(id)`, `.create(testsetId, {...})`, `.update(id, {...})`, `.delete({ ids })` |
| `list_systems`, `get_systems`, `upsert_systems`, `update_systems`, `delete_systems` | `client.systems.list(projectId)`, `.get(id)`, `.upsert(projectId, {...})`, `.update(id, {...})`, `.delete(id)` |
| `get_systems_versions`, `upsert_systems_versions` | `client.systems.versions.get(id)`, `client.systems.versions.upsert(systemId, {...})` |
| `list_metrics`, `get_metrics`, `create_metrics`, `update_metrics`, `delete_metrics` | `client.metrics.list(projectId)`, `.get(id)`, `.create(projectId, {...})`, `.update(id, {...})`, `.delete(id)` |
| `list_runs`, `get_runs`, `create_runs` | `client.runs.list(projectId)`, `.get(id)`, `.create(projectId, {...})` |
| `list_records`, `create_records`, `delete_records` | `client.records.list(runId)`, `.create(runId, {...})`, `.delete(id)` |
| `upsert_scores` | `client.scores.upsert(metricConfigId, { recordId, ... })` |
| `list_annotations` | `client.records.annotations.list(recordId)` |
| `search_docs` | Unchanged |

Record tags, record assignees, and session attachments were never exposed as tools but are available through `client.records.tags`, `client.records.assignees`, and `client.attachments`.

</Accordion>
