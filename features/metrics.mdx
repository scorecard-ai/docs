A **metric** turns one quality you care about, such as correctness, tone, or safety, into a repeatable score. Scorecard applies metrics to records and tracks the results across runs and over time.

Every metric has:

| Setting | Options |
| --- | --- |
| **Evaluation Type** | **AI**: a judge model scores each record from your guidelines. **Human**: a reviewer scores each record. **Heuristic (SDK)**: your Python or TypeScript function scores each record. |
| **Output Type** | **Boolean** (pass or fail), **Integer (1-5)**, or **Float (0.0-1.0)** |
| **Passing Threshold** | For Integer and Float metrics, the lowest score that passes |
| **Evaluation Guidelines** | Instructions for the judge model or the human reviewer |

## Start from a template

The Metrics page lists ready-made AI metrics below your own, each marked **Template**. Click **Add Metric** to add one to your project, then edit its guidelines for your domain.

| Template | Output type |
| --- | --- |
| Hallucination Detection | Integer (1-5) |
| Response Completeness | Integer (1-5) |
| User Intent Fulfillment | Integer (1-5) |
| Coherency | Integer (1-5) |
| Conciseness | Integer (1-5) |
| Source Attribution Quality | Integer (1-5) |
| Bias | Integer (1-5) |
| Personally Identifiable Information | Boolean |
| Content Moderation | Boolean |

Integer templates pass at 4 or higher. Templates read the whole record, so they work on traced records and on evaluation results alike.

## Create a metric

Click **New Metric**, choose the evaluation type and output type, set the passing threshold, and write your guidelines. Say what to reward, what to penalize, and include a short example if the call is subtle. Click **Create Metric** to save it.

### AI metrics

- **Basic** mode turns your guidelines into an evaluation prompt for you.
- **Advanced** mode lets you edit the full prompt template in Jinja, with a live preview against a testset or a run.

Only the prompt template is rendered as Jinja. Guidelines are inserted as plain text, so put any `{{ ... }}` variables in an Advanced-mode template. The template can use these variables:

| Variable | Contains |
| --- | --- |
| `{{ inputs.<field> }}` | One input field, from a testcase or your SDK call |
| `{{ outputs.<field> }}` | One output field your system returned |
| `{{ expected.<field> }}` | One expected output field from the testcase |
| `{{ allInputs }}`, `{{ allOutputs }}`, `{{ allExpected }}` | All inputs, outputs, or expected outputs as JSON. For traced records, `allInputs` and `allOutputs` hold the full trace. |
| `{{ guidelines }}` | The metric's guidelines |
| `{{ gradingInstructionsAndExamples }}` | Scorecard's instructions for the score format. Put it last. |

Jinja control flow works too, for example `{% if inputs.context %}Context: {{ inputs.context }}{% endif %}`.

<Note>
  The preview fills expected values only into `labels`, so `{{ expected.<field> }}` looks empty there but is filled when records are scored. Don't use `{{ labels }}` or `{{ metadata }}` in templates: they're empty at scoring time.
</Note>

Choose the judge under **Model**. The list shows models from providers your organization has added a key for under **Settings → AI Providers**, plus any custom models. If the chosen model's provider has no key in your organization, Scorecard scores with its default model. See [Model providers](/features/custom-provider).

### Human metrics

Human metrics get a pending score on every record in a run that uses them. Reviewers fill them in from the Records page or the [Compare page](/features/a-b-comparison), and several reviewers can score the same record. See [Human review](/features/human-review).

### Heuristic metrics

Write a function named `handler` in the metric editor. Scorecard calls it once per record. Return the score field for the metric's output type, as listed in [Scores and passing](#scores-and-passing), with an optional `reasoning` string:

<CodeGroup>
```python Python
def handler(*, inputs, outputs, expected, **kwargs):
    """kwargs also holds record_id, testcase_id, run_id, and metric_id."""
    response = str(outputs.get("response", ""))
    keyword = str(expected.get("keyword", ""))

    if keyword.lower() in response.lower():
        return {"binaryScore": True, "reasoning": "Keyword found in response"}
    return {"binaryScore": False, "reasoning": f"Missing keyword: {keyword}"}
```

```typescript TypeScript
async function handler(args: {
  inputs: Record<string, unknown>;
  outputs: Record<string, unknown>;
  expected: Record<string, unknown>;
  recordId: string;
  testcaseId: string | null;
  runId: string;
  metricId: string;
}) {
  const response = String(args.outputs.response ?? "");
  const keyword = String(args.expected.keyword ?? "");

  if (response.toLowerCase().includes(keyword.toLowerCase())) {
    return { binaryScore: true, reasoning: "Keyword found in response" };
  }
  return { binaryScore: false, reasoning: `Missing keyword: ${keyword}` };
}
```
</CodeGroup>

- Declare the function with `def handler(` or `function handler(`. Arrow functions aren't recognized.
- Each call has about 3 seconds. Network access is off unless you check **Allow Internet Access**.
- Use the standard library. Python has `json`, `re`, and `math` imported for you; other packages aren't guaranteed.
- Heuristic code is written in the metric editor. Metrics created through the API can't hold code, so to score with code that runs elsewhere, [push scores from your code](/features/push-scores) to a human metric instead.

### Create metrics from code

These examples assume `scorecard = Scorecard()` and `PROJECT_ID` set to your project ID:

<CodeGroup>
```python Python
metric = scorecard.metrics.create(
    PROJECT_ID,
    name="Answer matches reference",
    eval_type="ai",
    output_type="boolean",
    prompt_template=(
        "Question: {{ inputs.question }}\n"
        "Answer: {{ outputs.answer }}\n"
        "Reference: {{ expected.idealAnswer }}\n\n"
        "Pass if the answer states the same facts as the reference. Wording can differ.\n\n"
        "{{ gradingInstructionsAndExamples }}"
    ),
)
```

```typescript TypeScript
const metric = await scorecard.metrics.create(PROJECT_ID, {
  name: "Answer matches reference",
  evalType: "ai",
  outputType: "boolean",
  promptTemplate:
    "Question: {{ inputs.question }}\n" +
    "Answer: {{ outputs.answer }}\n" +
    "Reference: {{ expected.idealAnswer }}\n\n" +
    "Pass if the answer states the same facts as the reference. Wording can differ.\n\n" +
    "{{ gradingInstructionsAndExamples }}",
});
```
</CodeGroup>

Through the API, AI metrics default to `gpt-4o` as the judge. Set `eval_model_name` (`evalModelName`) to choose another model.

### Write reliable metrics

- **Score one thing per metric.** "Correct and polite" hides which half failed. Make two metrics and group them.
- **Prefer Boolean for hard rules** such as format, refusals, or leaked data, and Integer for judgment calls on a rubric.
- **Pilot on 10 to 20 records**, read the reasoning, and tighten the wording where the judge disagrees with you.
- **Check the judge against people.** Add a human metric with the same guidelines, have reviewers grade a sample, and compare the two. Where they disagree, fix the guidelines before you trust the AI metric on its own.

## Scores and passing

| Output type | Score | Passes when |
| --- | --- | --- |
| Boolean | `{"binaryScore": true, "reasoning": "..."}` | The score is `true` |
| Integer | `{"intScore": 4, "reasoning": "..."}` | The score is at or above the threshold (default 4) |
| Float | `{"floatScore": 0.87, "reasoning": "..."}` | The score is at or above the threshold |

New Float metrics default to a threshold of 0.5 in the app and 0.9 through the API, so set it explicitly. A run's passing rate counts passed and failed scores and leaves out pending ones and errors.

## When metrics run

- **Records added to a run** are scored with every metric on that run as soon as they're created, whether they come from the SDK, the API, a Kickoff Run, or GitHub Actions.
- **Traced records** aren't scored by default. Score them with **Score Records** on the [Records](/features/records) page, or [score a stream of traces as they arrive](/features/tracing#score-traces).
- **To re-score**, after editing a metric for example, use **Score Records** on the Records page or **Re-run Scoring** on a run. Re-scoring uses the latest version of each metric and never overwrites a completed human score.

## Metric groups

A metric group is a named set of metrics you apply together, for example everything you check on a RAG answer. Create one on the **Metric Groups** tab with **New Metric Group**, then select it when you start a [Kickoff Run](/features/runs#start-a-run-from-the-ui). On the Compare page, a group can show one Pass and Fail control per side. See [Score the pair](/features/a-b-comparison#score-the-pair).

## Versions and deletion

Changing a metric's configuration creates a new version, listed under **Version History** on the metric's page. Runs keep the versions they were scored with, and re-scoring uses the latest one.

Deleting a metric archives it and removes it from its groups. Its scores stop showing in the app but are still returned by the API and in exports.
