A **run** is a batch of records, usually your agent's outputs on one testset, scored with a chosen set of metrics. Every run is saved, so you can compare versions of your agent over time.

## Run from code

`run_and_evaluate` (Python) and `runAndEvaluate` (TypeScript) create a run, call your system once per testcase, and save each output as a record. Scorecard then scores the records in the background and the helper returns the run's ID and URL. The examples on this page assume `PROJECT_ID`, `TESTSET_ID`, and `METRIC_ID` hold your own IDs.

<CodeGroup>
```python Python
from scorecard_ai import Scorecard
from scorecard_ai.lib import run_and_evaluate

scorecard = Scorecard()


def system(inputs: dict, _system_version) -> dict:
    return {"answer": my_agent(inputs["question"])}


run = run_and_evaluate(
    client=scorecard,
    project_id=PROJECT_ID,
    testset_id=TESTSET_ID,
    metric_ids=[METRIC_ID],
    system=system,
)
print(run["url"])
```

```typescript TypeScript
import Scorecard, { runAndEvaluate } from "scorecard-ai";

const scorecard = new Scorecard();

const run = await runAndEvaluate(scorecard, {
  projectId: PROJECT_ID,
  testsetId: TESTSET_ID,
  metricIds: [METRIC_ID],
  system: async (inputs: { question: string }) => ({ answer: await myAgent(inputs.question) }),
});
console.log(run.url);
```
</CodeGroup>

Your `system` function receives a testcase's inputs and returns a flat object of outputs. Its keys are what metrics read as `{{ outputs.<key> }}`, so match them to your metric templates. In Python it's always called with two arguments, `(inputs, system_version)`, so a one-argument function raises a `TypeError`.

| Option | Python | TypeScript |
| --- | --- | --- |
| Use inline testcases instead of a testset | `testcases=[{"inputs": {...}, "expected": {...}}]` | `testcases: [{ inputs, expected }]` |
| Repeat each testcase to measure variance | `trials=3` | `runAndEvaluate(scorecard, args, { trials: 3 })` |
| Call your system in parallel | Not available; testcases run one at a time | `runAndEvaluate(scorecard, args, { runInParallel: true })` |
| Record which system version ran | `system_version_id=...` | `systemVersionId: ...` |

To attach each record's trace, give your `system` function an `options` parameter. See [Link traces to runs](/features/sdk-tracing).

The helper returns before scoring finishes. Open the URL, or poll `runs.get` until the run's status is `completed`, before you read results in code. To see every model and tool call behind a score, see [Link traces to runs](/features/sdk-tracing).

### Without the helper

To record outputs that already exist, such as logs or a batch job, create the run and records yourself. Each record is scored with the run's metrics when it's created:

<CodeGroup>
```python Python
run = scorecard.runs.create(PROJECT_ID, metric_ids=[METRIC_ID], testset_id=TESTSET_ID)

scorecard.records.create(
    run.id,
    testcase_id=TESTCASE_ID,  # optional
    inputs={"question": "How do I reset my password?"},
    outputs={"answer": "Go to Settings > Security."},
    expected={"idealAnswer": "Settings > Security > Reset password."},
)
```

```typescript TypeScript
const run = await scorecard.runs.create(PROJECT_ID, { metricIds: [METRIC_ID], testsetId: TESTSET_ID });

await scorecard.records.create(run.id, {
  testcaseId: TESTCASE_ID, // optional
  inputs: { question: "How do I reset my password?" },
  outputs: { answer: "Go to Settings > Security." },
  expected: { idealAnswer: "Settings > Security > Reset password." },
});
```
</CodeGroup>

`expected` is required; pass `{}` when there's none. To score records with your own checks instead of AI metrics, see [Push scores from your code](/features/push-scores).

## Start a run from the UI

**Kickoff Run** runs a testset without writing code. Open it from the sidebar (under **Advanced** in newer organizations), the Records page, or a testset's menu. Choose a testset and metrics (optionally filtered by a metric group), then a **Run Environment**:

- **Scorecard** runs a [prompt](/features/prompts) version on each testcase and saves the model's reply as the `response` output.
- **GitHub** starts your GitHub Actions workflow through the Scorecard GitHub app, so your real system produces the outputs. See [CI with GitHub Actions](/features/github-actions).

On a finished run, **Run Again** opens Kickoff Run with the same testset, system version, and metrics filled in.

## Read a run

The run page shows a card for each metric with its passing rate, mean and median, and score distribution, above a table with each testcase's inputs, outputs, and scores. Click a score to read its reasoning. To search, tag, assign, or export a run's records alongside others, filter the [Records](/features/records) page with `run.id:`.

- **Show Details** shows the run's notes, scoring cost, and configuration.
- **Re-run Scoring** re-scores selected records with the latest metric versions, without running your system again.
- **Export** downloads the records as CSV or Excel (XLSX).
- **Add Comparison** sets another run on the same testset next to this one. See [Compare runs](/features/a-b-comparison#compare-runs).

A run moves through these statuses:

| Status | Meaning |
| --- | --- |
| `awaiting_execution` | The run has testcases but no records yet |
| `running_execution` | Records are still being created |
| `running_scoring` | Records exist and some scores are pending. Pending human scores and scoring errors keep a run here. |
| `completed` | Every record has a score for every metric |

## Find runs

Newer organizations don't have **Runs** in the sidebar. Open a run from the link your code prints, or go to `app.scorecard.io/projects/<project_id>/runs` for the full list, which also charts metric history across recent runs.

## Systems and versions

A **system** is the agent you're testing, such as "Support agent". A **system version** is one configuration of it, such as a model and prompt. Tag runs with a version to see which configuration produced which scores, and to give runs readable names in [blind reviews](/features/a-b-comparison#blind-review).

<CodeGroup>
```python Python
system = scorecard.systems.upsert(PROJECT_ID, name="Support agent", config={"model": "gpt-4o-mini"})
version = scorecard.systems.versions.upsert(system.id, name="gpt-4o-mini", config={"model": "gpt-4o-mini"})

run = run_and_evaluate(
    client=scorecard,
    project_id=PROJECT_ID,
    testset_id=TESTSET_ID,
    metric_ids=[METRIC_ID],
    system_version_id=version.id,
    system=lambda inputs, system_version: {"answer": my_agent(inputs["question"], **system_version.config)},
)
```

```typescript TypeScript
const system = await scorecard.systems.upsert(PROJECT_ID, { name: "Support agent", config: { model: "gpt-4o-mini" } });
const version = await scorecard.systems.versions.upsert(system.id, { name: "gpt-4o-mini", config: { model: "gpt-4o-mini" } });

const run = await runAndEvaluate(scorecard, {
  projectId: PROJECT_ID,
  testsetId: TESTSET_ID,
  metricIds: [METRIC_ID],
  systemVersionId: version.id,
  system: async (inputs, systemVersion) => ({ answer: await myAgent(inputs.question, systemVersion.config) }),
});
```
</CodeGroup>

Upserting a version with the same config returns the existing version, so scripts are safe to re-run. In the app, **Advanced → Systems** lists systems; editing a system's configuration JSON saves a new version.
